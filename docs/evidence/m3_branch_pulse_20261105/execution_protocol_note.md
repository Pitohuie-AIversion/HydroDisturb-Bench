修正后的执行路径保留两类不同证据：

1. 从原 M3 的 `sol1 / solnum 901 / t=180 s` 取得完整原生向量，建立共同 checkpoint 和 `sol_branch_seed`。两分支载入的原生种子向量必须与原 M3 逐字节相同；不得来自规则采样张量。
2. 先预跑 Variables，读取同配置的初始化结果并核对两分支；此向量明确称为 `variables_preflight`，不冒充随后 Time 的内部输入。
3. 使用官方支持的 `runAll(false)`，在同一次调用中执行现有的编译、Variables 和 Time。初始化明确指向共同原生种子中的 180 s 保存状态（最新完整复制方案为第 901 帧，见下文）。保存实际求解日志及 `solver_first`（180 s 实际输出），分别核对来源配置和首帧差异。

真实准备记录显示，Variables 对 `u/v/p` 的差异约为 `10^-17`；辅助场 `spf.dt2Inv_u` 被重新计算。这不是新的物理初始条件，也不是从中继承原 BDF 历史。共同原生起点的证据由原生源/种子字节、实际初始化配置、求解日志及实际首帧比较共同组成，不能仅靠预检向量声称已观测到 Time 的内部缓存。

这是对执行方法与证据标签的修正。脉冲位置、方向、强度、起止时间、原生网格、材料/边界设置、求解容差、最大步长、输出时间表，以及冻结的重启/响应数值判据均不改变。第一次失败目录保留，修正后的运行使用新的独立目录。

官方 API 说明 `run/runFrom/runAll` 的布尔参数只控制默认绘图；`runAll` 执行完整现有求解序列：[COMSOL 6.4 model.sol()](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/comsol_api_general.47.58.html)。本文不把布尔参数解释为缓存保留开关。

## 原生导数缺项与检查点修正

第四次尝试使用 `runAll(false)` 后已进入 BDF，但在第一步 `180.0004 s` 非线性不收敛，未产生完整未来。没有为此调整容差、最大步长、牛顿迭代上限或扰动参数。

随后实际读取 `getUDot(901)` 发现：原 M3 的 88,483 项原生导数全有限，SHA-256 为 `a91258fc0f7fd9c9ea4b8ff67cb0a9efc597960892b4e7d285d733b87e358696`；手工构造的旧单帧种子的导数全零。之前仅检查 U 字节相同不足以证明必要的原生状态完整。缺失导数是实际查到的问题，但尚不能单凭此观察断言它是非线性失败的唯一原因。

检查点改为从原模型直接 `copySolution` 保留完整原生解及关联，不再通过 `setU/createSolution` 人工重建单帧。两分支仍以原始保存解编号 901、180 s 共同起步；同时核对源与种子的 U、UDot。种子由此前实现的第 1 帧改为原生第 901 帧只是解存储组织修正，物理起点及冻结参数均未改变。最终交付以真实成功回读和实验判据为准，不把任何准备成功视为未来轨迹已生成。

## 显式版本化的初始化变更

第五次零分支已完整保留并验证 U/UDot，仍在 `180.0004 s` 不收敛。因此不宣称补齐导数已经解决启动问题。

在尚无完整新轨迹时，单独登记 `restart_protocol_v2.json`：两分支均将 Time 节点的 `consistent` 从 `bweuler` 改为 `off`。这**确实改变了一个求解器初始化设置**，不能再声称相对基线所有非时间表设置均未改变。原计划文件保留，协议明确覆盖其中 `preserve_other_settings` 对这一项的限制；其他物理、时间积分及判据不变。

COMSOL 官方把 `Off` 定义为使用已有一致初值而不进行该项修正：[Time-Dependent Solver](https://doc.comsol.com/6.4/doc/com.comsol.help.comsol/comsol_ref_solver.36.139.html)。在本实验中这是基于已有保存解的受控初始化方案，不是已独立证明保存帧严格满足全部 DAE 约束。它仍必须通过原先冻结的零分支误差门和扰动响应门；如果失败，不更改阈值来通过。
